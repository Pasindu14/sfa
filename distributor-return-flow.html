Distributor Return Flow

What the system does when a distributor lowers a quantity while reviewing a pending bill — the records it writes, the stock it moves, and the one figure it deliberately refuses to subtract twice.

PATCH /api/v1/billings/{id}/adjust-items  ·  role: Distributor

First,

no separate return bill is ever created. The distributor doesn't author a return document, and there is no “add return line” control. They lower a quantity on the rep's original bill, and the system records the difference as a return line on that same bill. Everything below happens inside the bill the rep already submitted.

The sequence

Steps 4 to 7 commit as a single database transaction — the stock movement and the audit trail either both land or neither does.

  1. 01

    Rep submits the bill

    Stock is deducted here, at creation — not at approval. That single fact is why a later reduction has to give stock back rather than simply deduct less. The bill lands as Pending.

  2. 02

    Distributor lowers a quantity

    In the Review dialog. Quantities can only go down, never above what the rep billed. Zero is allowed; the line stays on the bill rather than being deleted.

  3. 03

    Guards run

    Is this my bill, is it still Pending, is the line a Sale or Free Issue, and is this actually a decrease. Any failure stops the request before a single row is written.

  4. 04

    Parent line is reduced and repriced

    Quantity drops to the new figure and the line's discount and total are recalculated on its own unchanged unit price.

    ┌ one transaction begins

  5. 05

    Return line is appended

    A new billing item for the difference, carrying the billed unit price and the parent's discount rate, and pointing back at the line it came from.

  6. 06

    Stock is credited back

    Into whichever pool the parent line originally drew from, with a ledger row recording the balance before and after.

  7. 07

    Audit trail is written

    Who changed what, from which quantity to which, and what the bill total was before and after.

    └ commit

  8. 08

    Distributor approves

    A deliberately separate action, so the recomputed total can be reviewed before it is committed. Approve stays disabled while edits are unsaved.

Worked example

The rep bills 10 × LKR 100.00 at a 10% line discount. The outlet took 7. The distributor changes the quantity to 7 and saves.

What changes on the bill
Field Before After
Sale line quantity 10 7
Sale line discount 100.00 70.00
Sale line total 900.00 630.00
OriginalQuantity null 10
Bill TotalAmount LKR 900.00 LKR 630.00
DistributorReturnValue 0.00 270.00
Normal stock on hand n n + 3

Every record written

Nine records across three areas, all from that one save.

On the bill

BillingItem (updated)
The parent sale line. Quantity 10 → 7, repriced, and OriginalQuantity stamped with 10 — on the first adjustment only, so 10 → 7 → 5 still reports 10.
BillingItem (new)
Qty 3 · unit price LKR 100.00, the billed price · discount rate 10% · total 270.00 · type Return · ReturnType = DistributorReturn · Source = DistributorReturn · SourceBillingItemId → the sale line.
Billing (header)
Totals rolled up, LastAdjustedAt set and AdjustmentCount incremented — which is what drives the “Adjusted” badge in the bill lists.

In stock

DistributorStock
QuantityOnHand increased by 3 on the pool the parent line drew from.
StockTransaction
The immutable ledger row: direction In, quantity 3, balance before and after snapshotted, referenced to Billing/{id}, transacted by the distributor user, noted “Distributor return on bill adjustment”.
Which pool
Sale → Normal
Free Issue, distributor-funded → Normal
Free Issue, company-funded → Free Issue

In the audit trail

BillingAdjustment
One per save round. Who, when, an optional note, and OldTotalAmount 900.00 → NewTotalAmount 630.00.
BillingAdjustmentLine
One per changed line. Product, qty 10 → 7, price 900.00 → 630.00, ReturnedQuantity 3, ReturnValue 270.00.
Notification + AuditLog
The rep is notified that quantities were adjusted, and the audit interceptor writes a row for every changed entity automatically.

The rule that matters

That 270.00 is recorded, never deducted

The sale line has already dropped from 900.00 to 630.00. Subtracting the return's value again would take the same 270.00 off twice. So it sums into DistributorReturnValue — not ReturnValue, which is subtracted from the bill total. The portal labels it “Distributor Returns (not deducted)” for exactly this reason.

Correct 900.00 → sale line reduced to 630.00 → total 630.00
Wrong 630.00 − 270.00 = 360.00  · the reduction counted twice

The same asymmetry protects your stock. If the bill is later rejected, the reversal deliberately skips these return lines and reverses only the reduced parent line — those 3 units were already handed back at adjustment time, and crediting them again would leave the pool 3 units richer than it started.

What the system refuses

Every guard rejects the whole request before anything is written. All return 422, except schema validation which returns 400.

Code Refused because
BILLING_QTY_INCREASE_NOT_ALLOWED A quantity was raised above what the rep billed. Reductions only ever credit stock, so an increase has no safe counterpart.
BILLING_LINE_NOT_ADJUSTABLE The line is a Return, not a Sale or Free Issue. Goods the outlet sent back aren't the distributor's to re-decide.
BILLING_ITEM_NOT_ON_BILL The line id belongs to a different bill.
BILLING_ALREADY_ACTIONED The bill has already been approved or rejected.
BILLING_NOT_ACTIONABLE The rep cancelled the bill.
BILLING_NO_CHANGES Nothing was actually reduced.
BILLING_ALL_LINES_ZERO Every line would go to zero — that's a rejection, not an adjustment, and the rep should be told so.
BILL_TOTAL_NEGATIVE The recomputed total would fall below zero.

One consequence worth stating plainly: if an outlet took more than was billed, this flow cannot express it. The rep writes a new bill.

Concurrency: the same advisory lock as approve, reject and cancel — billing:transition:{id} Ledger type: BillingReversal
